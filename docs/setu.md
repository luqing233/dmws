旧实现的问题：

- 默认请求 original，大图片增加等待时间。
- 使用 HTTP 流式响应后直接复制响应体，原请求超时不能约束整个复制过程。

- 参数分隔规则不识别带数字的 r18；size 列表又会被逗号拆散。
- 上游同时返回 error 和空 data 时，错误会被显示成没有找到图片。

## 当前行为

```text
涩图 tag=风景 num=2
涩图 风景 夜空 num=2
涩图 tag=风景 size=original,regular excludeai=true
```

默认 1 张、regular 尺寸、r18=0，数量为 1–5 张。
支持原有 `tag=` 写法和直接填写标签；最多 3 组标签，组内可用 `|` 表示任选其一。
size 支持 original、regular、small、thumb、mini。其余参数有 r18、proxy、excludeai。
参数无效时直接提示原因，不再悄悄使用默认值。非零 r18 保留主人/本群管理员权限检查，私聊只认可主人。

下载使用独立的 4 线程池、20 个排队位置，避免与等待下载的指令共用线程。
单次下载的重试共用 35 秒期限；完整响应体受限，批次最多等待 45 秒（含排队）。
超时取消未结束的任务；每张图限制 20 MiB；临时文件完成后原子替换为正式缓存，失败清理临时文件。
作品的标题、作者、来源在超时或下载繁忙时仍会保留。

线上进一步实测发现，默认 i.pixiv.re 代理下载约 749 KB 图片时，18 秒仅取得约 258 KB；
相同图片带 Referer 访问 i.pximg.net 源站约 0.5 秒完成。
因此默认代理的标准图片路径优先尝试源站，首次源站请求最多 12 秒，失败后回退代理，仍共用 35 秒总期限。
其他自定义代理地址保持原样。

## 转发格式

找到作品后，先回复“找到 N 张作品，正在加载图片…”。
作品集使用一个总览节点和每张作品各自的节点，最多 6 个节点：

```text
涩图 · 作品集
标签：风景
共 2 张 · 已加载 1 张 · 未加载 1 张
```

```text
1 / 2 ·《作品标题》
作者：画师名
作品来源：https://www.pixiv.net/artworks/作品编号
[图片，与以上说明放在同一节点]
```

未加载作品在自己的节点说明原因。来源优先使用 Pixiv 作品页，不在成功节点另塞一条长图片代理链接。
API 提供的文本在拼接图片 CQ 码之前转义，避免标题/作者被当成 CQ 指令。
全部下载失败时发送纯文字合并转发，保留标题、作者、作品页、图片链接和下载失败原因。
图片转发失败时再发送一次纯文字合并转发，不重复发送图片。每张作品占一个节点。
搜索无结果或图站请求失败时没有作品资料，仍使用简短的直接回复。
如果QQ连纯文字合并转发也拒绝，最后仅直接提示发送失败，不把作品链接逐条刷到会话里。
异常细节只记服务器日志，用户收到可读提示。
